### 학습 내용

#### 1. Chapter 07 - REST API (`02_spring_boot/chap07_rest-api`)

##### 1-1. ResponseEntity — HTTP 응답 전체를 직접 제어하는 객체

`@RestController`에서 단순히 객체를 반환하면 Spring이 HTTP 응답을 알아서 만들어주지만, 상태코드나 헤더를 직접 지정하고 싶을 때는 `ResponseEntity`를 사용한다.

```java
// 방법 1: 생성자로 직접 구성
return new ResponseEntity<>(responseMessage, headers, HttpStatus.OK);

// 방법 2: 정적 팩토리 메서드 체이닝
return ResponseEntity
        .ok()
        .headers(headers)
        .body(responseMessage);
```

- 제네릭 타입으로 응답 body의 타입을 지정한다. body가 없을 때는 `ResponseEntity<Void>`를 쓰고 `.build()`로 완성한다.
- `HttpHeaders` 객체를 만들어 `setContentType` 등으로 헤더를 설정한 뒤 `ResponseEntity`에 함께 넘긴다.

##### 1-2. CRUD 엔드포인트별 HTTP 상태코드 패턴

```java
// GET — 200 OK + body
return ResponseEntity.ok().headers(headers).body(responseMessage);

// POST — 201 Created + Location 헤더 (body 없음)
return ResponseEntity
        .created(URI.create("/api/v1/response/users/" + newUser.getNo()))
        .build();

// PUT — 204 No Content (body 없음)
return ResponseEntity.noContent().build();

// DELETE — 204 No Content (body 없음)
return ResponseEntity.noContent().build();
```

- POST로 새 리소스를 만들면 `201 Created`와 함께 `Location` 헤더로 새 리소스의 URI를 알려주는 것이 HTTP 관례다.
- 수정·삭제는 돌려줄 데이터가 없으므로 `204 No Content`를 쓴다.

##### 1-3. HTTP 상태코드 정리

200 OK
- 조회 성공
- 응답 body 있음

201 Created
- 새 리소스 생성 성공
- Location header로 새 리소스 위치 안내 가능

204 No Content
- 요청 처리 성공
- 응답 body 없음
- 수정/삭제 성공에 자주 사용

##### 1-4. 공통 응답 구조 — ResponseMessage DTO

응답 body 구조를 일정하게 맞추기 위한 DTO. 성공 응답을 항상 같은 형태로 내려주기 위해 wrapper 역할을 한다.

```java
@AllArgsConstructor
@Getter
public class ResponseMessage {
    private int httpStatus;
    private String message;
    private Map<String, Object> results; // 실제 데이터는 여기에 "users", "user" 등의 키로 담음
}
```

- `results` 필드를 `LinkedHashMap`으로 구성하면 삽입 순서를 유지해 JSON 직렬화 순서가 보장된다.
- 컨트롤러 코드는 항상 이 구조로 응답하므로 프론트엔드가 응답 파싱 로직을 통일할 수 있다.

##### 1-5. Stream + filter로 조건 검색 구현

리스트 기반 인메모리 데이터에서 `@RequestParam`으로 받은 조건(name, status)으로 필터링하는 패턴.

```java
List<UserDto> foundUsers = users.stream()
        .filter(user -> {
            if (status != null && !user.getStatus().equals(status)) return false;
            if (name != null && !user.getName().contains(name)) return false;
            return true;
        }).toList();
```

- `@RequestParam(required = false)` → 쿼리 파라미터가 없으면 null이 들어오므로 null 체크 후 조건 적용.
- null이면 해당 조건을 무시(= 전체 조회)하는 식으로 동적 필터링을 구현한다.

#### 2. Bean Validation — 요청 객체 필드 검증 (`section02`)

##### 2-1. Bean Validation 어노테이션

DTO 필드에 규칙 어노테이션을 붙여두고, 컨트롤러에서 `@Valid`를 달면 Spring이 자동으로 검증한다.

```java
public class UserDto {
    @NotNull(message = "아이디는 반드시 입력되어야 합니다.")
    @NotBlank(message = "아이디는 공백일 수 없습니다.")
    private String id;

    @NotNull(message = "비밀번호는 반드시 입력되어야 합니다.")
    @Length(max = 10, message = "비밀번호는 길이 10을 초과할 수 없습니다.")
    private String pwd;

    @NotBlank(message = "이름은 공백일 수 없습니다.")
    @Size(max = 10, message = "이름은 길이 10을 초과할 수 없습니다.")
    private String name;

    @Past(message = "가입일은 현재보다 과거 날짜가 입력되어야 합니다.")
    private Date enrollDate;
}
```

- `@NotNull` vs `@NotBlank`: `@NotNull`은 null만 막고, `@NotBlank`는 null + 공백 문자열도 막는다.
- `@Length`는 Hibernate Validator 전용, `@Size`는 Bean Validation 표준이다.
- `@Past`는 날짜가 현재보다 과거인지 검증한다.

##### 2-2. @Valid로 검증 트리거

```java
@PostMapping("/users")
public ResponseEntity<Void> registUser(@Valid @RequestBody UserDto user) {
    return ResponseEntity.created(URI.create("/api/v1/validation/users/1")).build();
}
```

- `@Valid`가 붙으면 Spring이 컨트롤러 메서드 진입 전에 `UserDto` 필드를 검증한다.
- 검증 실패 시 `MethodArgumentNotValidException`이 발생하며 컨트롤러 코드는 실행되지 않는다.

##### 2-3. @RestControllerAdvice로 검증 예외 처리

```java
@RestControllerAdvice
public class ExceptionController {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> methodValidException(MethodArgumentNotValidException e) {
        String detail = e.getBindingResult().getFieldError().getDefaultMessage();
        String bindResultCode = e.getBindingResult().getFieldError().getCode();

        String code, description;
        switch (bindResultCode) {
            case "NotNull": code = "ERROR_CODE_0001"; description = "필수 값이 누락되었습니다."; break;
            case "NotBlank": code = "ERROR_CODE_0002"; description = "필수 값이 공백입니다."; break;
            case "Size":    code = "ERROR_CODE_0003"; description = "글자 수를 확인해주세요."; break;
            default:        code = "ERROR_CODE_9999"; description = "요청 값 검증에 실패했습니다.";
        }
        return new ResponseEntity<>(new ErrorResponse(code, description, detail), HttpStatus.BAD_REQUEST);
    }

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> UserException(UserNotFoundException e) {
        return new ResponseEntity<>(
            new ErrorResponse("ERROR_CODE_0000", "회원 정보 조회 실패", e.getMessage()),
            HttpStatus.NOT_FOUND
        );
    }
}
```

- `getBindingResult().getFieldError().getCode()`로 어떤 어노테이션 검증이 실패했는지 알 수 있다.
- `getDefaultMessage()`는 어노테이션의 `message` 속성에 적어둔 문자열이 반환된다.
- 검증 실패는 `400 Bad Request`, 리소스 없음은 `404 Not Found`로 명확히 구분한다.

##### 2-4. 커스텀 예외 클래스 — UserNotFoundException

```java
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) {
        super(message);
    }
}
```

- `RuntimeException` 상속 → unchecked exception이므로 `throws` 선언 없이 컨트롤러 어디서든 던질 수 있다.

#### 3. Swagger(SpringDoc OpenAPI) — API 문서 자동화 (`section03`)

##### 3-1. SwaggerConfig — OpenAPI Bean 등록

```java
@Configuration
public class SwaggerConfig {

    @Bean
    public OpenAPI openAPI() {
        return new OpenAPI().info(swaggerInfo());
    }

    private Info swaggerInfo() {
        return new Info()
                .title("Ohgiraffers API")
                .description("SpringBoot Swagger 연동 테스트")
                .version("1.0.0");
    }
}
```

- `springdoc-openapi` 라이브러리가 클래스패스에 있으면 `/swagger-ui/index.html`에서 Swagger UI에 접근할 수 있다.
- `OpenAPI` Bean을 등록해 API 제목·설명·버전 등 메타 정보를 설정한다.

##### 3-2. 컨트롤러·메서드에 문서화 어노테이션 추가

```java
@Tag(name = "user 관련 api", description = "회원 조회, 등록, 수정, 삭제 API")
@RestController
public class SwaggerTestController {

    @Operation(summary = "회원 목록 조회/검색",
               description = "전체 회원을 조회하거나 name, status query string으로 검색한다.")
    @ApiResponses({
        @ApiResponse(responseCode = "200", description = "회원 목록 조회 성공")
    })
    @GetMapping("/users")
    public ResponseEntity<ResponseMessage> findUserByConditions(...) { ... }
}
```

- `@Tag` → 컨트롤러 단위로 API 그룹 이름과 설명을 붙인다.
- `@Operation` → 각 엔드포인트의 요약(summary)과 상세 설명(description)을 지정한다.
- `@ApiResponses` / `@ApiResponse` → 이 엔드포인트가 반환할 수 있는 HTTP 상태코드와 설명을 명시한다. Swagger UI에서 예상 응답 목록으로 표시된다.

### 핵심 정리

ResponseEntity 사용 원칙
- 응답 body + 헤더 + 상태코드를 함께 제어할 때 사용
- GET 200 / POST 201 Created + Location 헤더 / PUT·DELETE 204 No Content 패턴 준수
- body 없을 때는 `ResponseEntity<Void>` + `.build()`

HTTP 상태코드 요약
- 200 OK: 조회 성공, 응답 body 있음
- 201 Created: 새 리소스 생성 성공, Location header로 위치 안내 가능
- 204 No Content: 요청 처리 성공, 응답 body 없음, 수정/삭제에 자주 사용

ResponseMessage
- 응답 body 구조를 일정하게 맞추기 위한 DTO
- `results` Map에 실제 데이터를 키-값으로 담아 프론트엔드 파싱 로직 통일

Bean Validation 흐름
- DTO 필드에 `@NotNull`, `@NotBlank`, `@Size`, `@Past` 등 어노테이션으로 규칙 정의
- 컨트롤러 `@Valid @RequestBody`로 검증 트리거 → 실패 시 `MethodArgumentNotValidException` 발생
- `@RestControllerAdvice` + `@ExceptionHandler`로 검증 예외를 JSON 에러 응답으로 변환
- 에러 응답 구조: `code`(에러 코드) + `description`(에러 종류) + `detail`(구체적 메시지)

Swagger 적용 방법
- 의존성 추가 후 `SwaggerConfig`에서 `OpenAPI` Bean 등록
- `@Tag` → 컨트롤러 그룹화, `@Operation` → 메서드 설명, `@ApiResponse` → 응답 코드 명세
- `/swagger-ui/index.html` 접속으로 UI 확인 및 직접 API 테스트 가능

### 느낀 점 / 회고

이번 챕터는 Spring Boot로 REST API를 실제 표준에 맞게 내려주는 방법을 한 번에 잡은 느낌이었다. `ResponseEntity`를 쓰기 전까지는 상태코드를 어떻게 직접 지정하는지 몰랐는데, POST는 `201 Created` + `Location` 헤더, PUT·DELETE는 `204 No Content`라는 패턴이 단순히 규칙이 아니라 HTTP 스펙의 의도에서 나온 것임을 이해하니 자연스럽게 외워졌다.

Bean Validation에서 `@Valid` 하나만 붙이면 컨트롤러 진입 전에 검증이 끝난다는 것, 그리고 실패 시 `MethodArgumentNotValidException`이 던져지므로 `@RestControllerAdvice`에서 `getBindingResult().getFieldError().getCode()`로 어떤 어노테이션이 실패했는지까지 파악할 수 있다는 게 실용적이었다. 이 코드 값(`NotNull`, `NotBlank` 등)을 switch로 분기해서 에러 코드 체계를 만드는 패턴은 실제 업무에서도 그대로 쓸 수 있는 구조라는 생각이 들었다.

Swagger는 `@Tag`, `@Operation`, `@ApiResponse` 세 어노테이션의 역할이 명확하게 나뉜다는 게 좋았다. 코드에 문서가 붙어있으니 별도 API 명세 문서를 관리하지 않아도 된다는 장점이 직관적으로 와닿았다. 다음에 실제 프로젝트에 붙일 때 `@ApiResponse`에 응답 schema까지 연결하는 부분도 찾아봐야겠다.
