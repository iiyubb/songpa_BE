### 학습 내용

#### 1. Chapter 03 - 어노테이션 기반 DI (`chap03_di-annotation`)

이번 챕터는 XML/JavaConfig로 일일이 빈을 등록하던 방식에서 벗어나, **어노테이션 + 컴포넌트 스캔**으로 빈 등록과 의존성 주입을 자동화하는 방식을 다뤘다.

##### 1-1. 컴포넌트 스캔과 스테레오타입 어노테이션
`AnnotationConfigApplicationContext`에 **패키지 경로**를 넘기면, 해당 패키지 하위를 스캔해서 스테레오타입 어노테이션이 붙은 클래스를 자동으로 빈으로 등록한다.

```java
// com.ohgiraffers 패키지 하위를 스캔해서 빈 자동 등록
ApplicationContext context = new AnnotationConfigApplicationContext("com.ohgiraffers");
```

| 어노테이션 | 용도 (계층) |
| --- | --- |
| `@Component` | 범용 빈 등록 |
| `@Service` | 비즈니스 로직 (Service 계층) |
| `@Repository` | DB 접근 (DAO/Repository 계층) |
| `@Controller` | 요청 처리 (이번 챕터엔 미등장) |

- `@Service`, `@Repository`는 모두 `@Component`의 **세분화된 종류**다. 기능 차이보다 "역할 표시(가독성·계층 구분)" 목적이 크다.
- 빈 이름을 직접 지정할 수 있다: `@Service("bookServiceField")`, `@Repository("bookDAO")`. 생략하면 클래스명 첫 글자를 소문자로 바꾼 이름이 기본값.

```java
@Repository("bookDAO")
public class BookDAOImpl implements BookDAO { ... }
```

#### 2. @Autowired - 3가지 의존성 주입 방식 (`section01/autowired`)

`@Autowired`는 **해당 타입과 일치하는 빈을 찾아 자동으로 주입**한다. 주입 위치에 따라 세 가지 방식이 있다.

##### 2-1. 필드 주입 (Field Injection)

```java
@Service("bookServiceField")
public class BookService {

    @Autowired
    private BookDAO bookDAO;   // 필드에 바로 주입

    public List<BookDTO> selectAllBooks() {
        return bookDAO.selectBookList();
    }
}
```

- 코드는 가장 간결하지만 **권장되지 않는 방식**.
- `final` 선언 불가, 외부에서 주입 교체가 어려워 테스트가 까다롭다. 순환참조도 런타임에야 드러난다.

##### 2-2. Setter 주입 (Setter Injection)

```java
@Service("bookServiceSetter")
public class BookService {

    private BookDAO bookDAO;

    @Autowired
    public void setBookDAO(BookDAO bookDAO) {
        this.bookDAO = bookDAO;
    }
}
```

- 주입이 **선택적**이거나 런타임에 의존성을 바꿔야 할 때 사용.
- 객체 생성 후 setter가 호출되므로 `final`을 쓸 수 없다.

##### 2-3. 생성자 주입 (Constructor Injection) — 실무 기본

```java
@Service("bookServiceConstructor")
public class BookService {

    private final BookDAO bookDAO;   // final 가능

    @Autowired   // 생성자가 하나면 생략 가능
    public BookService(BookDAO bookDAO) {
        this.bookDAO = bookDAO;
    }
}
```

- **실무에서 가장 권장되는 기본 방식.**
- `final`로 불변성 보장, 객체 생성 시점에 의존성이 모두 채워지므로 **주입 누락 시 컴파일/기동 단계에서 바로 발견**.
- 순환참조를 기동 시점에 잡아낼 수 있고, 테스트 시 생성자로 mock 주입이 쉽다.
- 생성자가 **하나뿐이면 `@Autowired` 생략 가능**.

| 방식 | final | 권장도 | 특징 |
| --- | --- | --- | --- |
| 필드 | X | △ | 간결하나 테스트·교체 어려움 |
| Setter | X | ○ | 선택적/가변 의존성 |
| 생성자 | O | ◎ | 불변·누락 조기 발견 (기본) |

#### 3. 같은 타입 빈이 여러 개일 때 (`section02`)

`Pokemon` 인터페이스를 구현한 빈이 여러 개(`Pikachu`, `Charmander`, `Squirtle`)일 때, `@Autowired Pokemon pokemon`은 **어떤 빈을 넣어야 할지 몰라 `NoUniqueBeanDefinitionException`** 이 발생한다. 이를 해결하는 방법들.

##### 3-1. @Primary - 우선순위 지정 (`annotation/primary`)
동일 타입 빈 중 **우선적으로 연결할 기본 빈**을 지정한다.

```java
@Component
@Primary   // 동일 타입 여러 빈 중 이 빈을 우선 주입
public class Charmander implements Pokemon {
    @Override
    public void attack() { System.out.println("..."); }
}
```

```java
@Service("pokemonServicePrimary")
public class PokemonService {

    private final Pokemon pokemon;

    @Autowired
    public PokemonService(Pokemon pokemon) {   // @Primary가 붙은 Charmander 주입됨
        this.pokemon = pokemon;
    }
}
```

##### 3-2. @Qualifier - 이름으로 특정 빈 지정
빈 이름을 직접 지목해서 주입한다. `@Primary`보다 **우선순위가 높다.**

```java
@Qualifier("pikachu")   // pikachu라는 이름의 빈을 주입
private final Pokemon pokemon;
```

> `@Primary`는 "기본값", `@Qualifier`는 "명시적 지목". 둘이 함께 있으면 `@Qualifier`가 이긴다.

##### 3-3. 컬렉션 주입 - 같은 타입 빈을 전부 받기 (`annotation/collection`)
하나만 고르는 대신 **같은 타입의 빈을 List로 모두 주입**받을 수 있다.

```java
@Service("pokemonServiceCollection")
public class PokemonService {

    private final List<Pokemon> pokemonList;

    @Autowired
    public PokemonService(List<Pokemon> pokemonList) {   // Pokemon 구현 빈 전부 주입
        this.pokemonList = pokemonList;
    }

    public void pokemonAttack() {
        pokemonList.forEach(Pokemon::attack);   // 등록된 모든 포켓몬 공격
    }
}
```

- 전략 패턴처럼 **같은 인터페이스의 여러 구현체를 한꺼번에 다뤄야 할 때** 유용하다. (예: 여러 알림 채널, 여러 결제 수단)

build.gradle 의존성:
```gradle
implementation 'org.springframework:spring-context:7.0.7'
implementation 'org.springframework:spring-core:7.0.7'
```

### 느낀 점 / 회고

그동안 Spring Boot에서 `@Service`, `@Repository`, 생성자 주입을 거의 관습처럼 써왔는데, 이번에 컴포넌트 스캔부터 직접 보니 "어노테이션 하나로 빈이 등록되고 타입이 맞는 걸 자동으로 꽂아준다"는 게 어떤 과정인지 정리됐다. 특히 세 가지 주입 방식을 한 챕터에서 같은 `BookService`로 비교해보니, 왜 생성자 주입이 실무 기본인지(불변성, 주입 누락 조기 발견, 테스트 용이성) 말로만 외우던 걸 코드로 체감했다.

section02의 `@Primary` / `@Qualifier` / 컬렉션 주입은 면접에서 "같은 타입 빈이 여러 개면 어떻게 처리하냐"는 질문으로 자주 나오는 부분이라 직접 돌려본 게 도움이 됐다. 특히 `List<Pokemon>`로 구현체 전부를 받아 순회하는 패턴은, 예전에 알림이나 채널을 전략 패턴으로 처리하던 상황과 똑같아서 "아 이래서 스프링이 전략 패턴 구현을 편하게 해준다고 하는구나" 싶었다. AI Agent 쪽에서도 여러 LLM provider나 tool 구현체를 인터페이스로 추상화해서 컬렉션으로 주입받는 식으로 응용할 수 있을 것 같다.
