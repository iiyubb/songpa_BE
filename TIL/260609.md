#### 1. Chapter 05 - Spring MyBatis 완성 (`10_mybatis/chap05_spring-mybatis`)

##### 1-1. Service — SELECT vs DML 트랜잭션 패턴 구분

```java
// 조회 : 데이터 변경이 없으므로 commit/rollback 불필요 → try-finally
public List<MenuDTO> selectAllMenu() {
    SqlSession sqlSession = getSqlSession();
    try {
        return sqlSession.getMapper(MenuMapper.class).selectAllMenu();
    } finally {
        sqlSession.close();
    }
}

// DML : 데이터 변경 → try-catch-finally + commit/rollback
public boolean registMenu(MenuDTO menu) {
    SqlSession sqlSession = getSqlSession();
    try {
        int result = sqlSession.getMapper(MenuMapper.class).insertMenu(menu);
        if (result > 0) sqlSession.commit();
        else            sqlSession.rollback();
        return result > 0;
    } catch (RuntimeException e) {
        sqlSession.rollback();
        throw e;
    } finally {
        sqlSession.close();
    }
}
```

##### 1-2. Mapper XML — INSERT / UPDATE / DELETE

```xml
<insert id="insertMenu" parameterType="com.ohgiraffers.section03.remix.MenuDTO">
    INSERT INTO tbl_menu (menu_name, menu_price, category_code, orderable_status)
    VALUES ( #{ name }, #{ price }, #{ categoryCode }, 'Y' )
</insert>

<update id="updateMenu" parameterType="com.ohgiraffers.section03.remix.MenuDTO">
    UPDATE tbl_menu
    SET menu_name = #{name}, menu_price = #{price}, category_code = #{categoryCode}
    WHERE menu_code = #{code}
</update>

<delete id="deleteMenu" parameterType="com.ohgiraffers.section03.remix.MenuDTO">
    DELETE FROM tbl_menu
    WHERE menu_code = #{code}
</delete>
```

#### 2. Chapter 00 - JPA 도입 배경: JDBC 직접 SQL의 문제점 (`11_jpa/chap00-intro`)

JPA를 왜 쓰는지 이해하기 위해 순수 JDBC로 직접 SQL을 쓸 때의 문제 4가지를 테스트로 확인했다.

##### 2-1. 문제 1 — 반복 코드 (데이터 변환 + SQL + JDBC API)

```java
// 조회 한 번에 필요한 코드 전체
Statement stmt = con.createStatement();
ResultSet rset = stmt.executeQuery("SELECT MENU_CODE, MENU_NAME, ... FROM TBL_MENU");

List<Menu> menuList = new ArrayList<>();
while(rset.next()) {
    Menu menu = new Menu();
    menu.setMenuCode(rset.getInt("MENU_CODE"));      // ResultSet → 객체 변환
    menu.setMenuName(rset.getString("MENU_NAME"));   // 컬럼 개수만큼 반복
    // ...
    menuList.add(menu);
}
rset.close();
stmt.close();
```

테이블마다, 기능마다 이 코드를 반복 작성해야 한다 → 개발 시간 증가, 유지보수성 악화.

##### 2-2. 문제 2 — SQL 의존적인 개발

```java
// 처음에는 MENU_CODE, MENU_NAME만 조회하는 SQL 작성
String query = "SELECT MENU_CODE, MENU_NAME FROM TBL_MENU";

// 그런데 MENU_PRICE도 필요해져서 Java 코드에도 손댐
menu.setMenuPrice(rset.getInt("MENU_PRICE"));  // SQL에 없는 컬럼 → 런타임 오류
```

SQL이 바뀌면 Java 매핑 코드도 함께 수정해야 하고, SQL이 바뀌면 Java 코드가 깨질 수 있다.

##### 2-3. 문제 3 — 패러다임 불일치 (상속 / 연관관계)

**상속 불일치**
- 객체지향: 슈퍼클래스 속성을 서브클래스가 그대로 공유
- DB: 슈퍼타입/서브타입 테이블이 물리적으로 분리 → INSERT 2번 필요

```java
// JDBC 직접 : 회원 테이블 + 법인회원 테이블에 각각 INSERT
// JPA 사용 : entityManager.persist(법인회원) 한 번으로 해결
```

**연관관계 불일치**
```java
// DB에 맞춘 객체 모델 (FK를 int로 보관)
class Menu {
    private int categoryCode;  // 단순 FK 숫자
}

// 객체지향에 맞는 모델 (참조로 보관)
class Menu {
    private Category category;  // 연관 객체를 직접 참조
}
```

JDBC는 연관 데이터를 가져오려면 JOIN 쿼리를 직접 작성하고 수동으로 매핑해야 한다.

```java
// 연관 데이터 조회 시 JOIN + 수동 매핑
String query = "SELECT A.*, B.CATEGORY_CODE, B.CATEGORY_NAME "
             + "FROM TBL_MENU A JOIN TBL_CATEGORY B ON (A.CATEGORY_CODE = B.CATEGORY_CODE)";

menuAndCategory.setCategory(
    new Category(rset.getInt("CATEGORY_CODE"), rset.getString("CATEGORY_NAME"))
);
```

##### 2-4. 문제 4 — 동일성 보장 불가

```java
// 같은 행을 두 번 조회해도 다른 객체 인스턴스가 생성됨
Menu menu1 = /* SELECT WHERE MENU_CODE = 1 */;
Menu menu2 = /* SELECT WHERE MENU_CODE = 1 */;

menu1 == menu2               // false — 다른 인스턴스
menu1.getMenuName().equals(menu2.getMenuName())  // true — 값은 같음
```

JPA는 같은 EntityManager 스코프 안에서 동일한 PK로 조회하면 항상 같은 인스턴스를 반환해 동일성을 보장한다.

#### 3. Chapter 01 - 영속성 컨텍스트와 EntityManager (`11_jpa/chap01_persistance-context`)

##### 3-1. `persistence.xml` — JPA 설정 파일

`src/main/resources/META-INF/persistence.xml` 위치에 위치해야 JPA가 자동으로 찾는다.

```xml
<persistence-unit name="jpatest">
    <class>com.ohgiraffers.section02.crud.Menu</class>

    <properties>
        <property name="jakarta.persistence.jdbc.driver" value="com.mysql.cj.jdbc.Driver"/>
        <property name="jakarta.persistence.jdbc.url" value="jdbc:mysql://localhost:3306/menudb"/>
        <property name="jakarta.persistence.jdbc.user" value="ohgiraffers"/>
        <property name="jakarta.persistence.jdbc.password" value="ohgiraffers"/>
        <property name="hibernate.show_sql" value="true"/>
        <property name="hibernate.format_sql" value="true"/>
    </properties>
</persistence-unit>
```

- `persistence-unit name` : EntityManagerFactory 생성 시 이 이름으로 식별
- `<class>` : 관리할 엔티티 클래스 명시

##### 3-2. EntityManagerFactory vs EntityManager 생명주기

```java
// EntityManagerFactory : 앱 전체에서 하나 (싱글톤)
public class EntityManagerFactoryGenerator {
    private static EntityManagerFactory factory
            = Persistence.createEntityManagerFactory("jpatest");

    public static EntityManagerFactory getInstance() {
        return factory;  // 항상 같은 인스턴스
    }
}

// EntityManager : 요청마다 새로 생성
public class EntityManagerGenerator {
    public static EntityManager getInstance() {
        return EntityManagerFactoryGenerator.getInstance().createEntityManager();
        // 호출마다 다른 인스턴스
    }
}
```

| 객체 | 범위 | 생성 횟수 |
|---|---|---|
| `EntityManagerFactory` | 앱 전체 | 딱 하나 (싱글톤) |
| `EntityManager` | 요청 하나 | 매번 새로 생성 |

테스트로 직접 확인:
```java
// Factory — 싱글톤 검증
assertEquals(factory1, factory2);      // 같은 인스턴스

// EntityManager — 요청마다 새 인스턴스 검증
assertNotEquals(manager1, manager2);   // 다른 인스턴스
```

##### 3-3. Entity 클래스 — JPA 매핑 어노테이션

```java
@Entity(name = "Section02Menu")    // JPA가 관리하는 엔티티, JPQL에서 사용할 별칭
@Table(name = "tbl_menu")          // 매핑할 DB 테이블명
public class Menu {

    @Id
    @Column(name = "menu_code")    // PK 컬럼
    private int menuCode;

    @Column(name = "menu_name")
    private String menuName;

    @Column(name = "menu_price")
    private int menuPrice;

    @Column(name = "category_code")
    private int categoryCode;

    @Column(name = "orderable_status")
    private String orderableStatus;

    protected Menu() {}  // JPA는 기본 생성자 필수 (리플렉션으로 인스턴스 생성)
}
```

- `@Entity` : 이 클래스가 JPA 엔티티임을 선언. 이 어노테이션이 있어야 JPA가 관리
- `@Table(name)` : 클래스명과 테이블명이 다를 때 명시
- `@Id` : PK 컬럼 지정
- `@Column(name)` : 필드명과 DB 컬럼명이 다를 때 명시

##### 3-4. EntityManager — `find()`로 조회

```java
public Menu findMenuByMenuCode(int menuCode) {
    EntityManager entityManager = EntityManagerGenerator.getInstance();
    return entityManager.find(Menu.class, menuCode);  // (엔티티 타입, PK)
}
```

```java
// 파라미터화 테스트로 여러 PK 값 검증
@ParameterizedTest
@CsvSource({"2,2", "3,3"})
void testFindMenuByMenuCode(int menuCode, int expected) {
    Menu foundMenu = crud.findMenuByMenuCode(menuCode);
    assertEquals(expected, foundMenu.getMenuCode());
}
```

- `find(EntityClass, pk)` : PK로 단건 조회. 없으면 `null` 반환
- 같은 EntityManager 스코프에서 같은 PK로 find하면 동일 인스턴스 반환 (동일성 보장)

### 핵심 정리

JDBC 직접 SQL의 4가지 문제

| 문제 | 증상 | JPA 해결책 |
|---|---|---|
| 반복 코드 | 테이블마다 Connection/Statement/ResultSet 변환 코드 | 엔티티 매핑으로 자동 처리 |
| SQL 의존성 | SQL 변경 → Java 코드도 수정 필요 | 메서드 호출로 쿼리 자동 생성 |
| 패러다임 불일치 | 상속/연관관계를 DB 구조에 억지로 맞춤 | 객체 모델 그대로 사용 |
| 동일성 미보장 | 같은 행 조회 = 다른 객체 | 영속성 컨텍스트가 1차 캐시로 동일 인스턴스 보장 |

EntityManager 생명주기
- `EntityManagerFactory` → 앱 전체 싱글톤, `Persistence.createEntityManagerFactory("이름")`으로 생성
- `EntityManager` → 요청 하나의 스코프, `factory.createEntityManager()`로 매번 새로 생성

JPA 필수 설정 파일
- `persistence.xml` : `META-INF/` 하위에 위치, persistence-unit 이름 + DB 연결 정보 + 엔티티 클래스 목록
- `hibernate.show_sql=true` : 실행 SQL 콘솔 출력 (개발 환경에서 쿼리 확인용)

엔티티 클래스 필수 조건
- `@Entity` 선언
- `@Id`로 PK 지정
- 기본 생성자 필수 (`protected` 이상) — JPA가 리플렉션으로 인스턴스를 생성하기 때문

### 느낀 점 / 회고

오늘은 MyBatis CRUD를 완전히 마무리하고 JPA의 첫 챕터를 시작했다.

chap05 spring-mybatis에서 insert/update/delete를 직접 작성하면서 DML의 트랜잭션 패턴이 명확하게 손에 익었다. SELECT는 `try-finally`로 닫기만 하고, DML은 `try-catch-finally`에서 성공 여부에 따라 `commit/rollback`, 예외 발생 시 `catch`에서 rollback 후 재throw. 이 패턴을 반복하다 보니 "왜 Spring의 `@Transactional`이 편한지"를 몸으로 이해하게 됐다.

JPA 도입 배경으로 JDBC의 4가지 문제점을 테스트 코드로 직접 확인한 게 인상적이었다. 특히 동일성 보장 문제는 `menu1 == menu2`가 `false`라는 테스트로 처음 명확하게 짚어봤다. 같은 DB 행이지만 두 번 조회하면 힙에 두 개의 객체가 생기는 것 — 컬렉션에서 중복 제거나 equals 비교를 할 때 은근히 버그가 생길 수 있다는 게 납득됐다.

JPA의 `EntityManagerFactory`와 `EntityManager` 생명주기는 MyBatis의 `SqlSessionFactory`/`SqlSession`과 구조가 거의 같았다. 팩토리는 앱 전체 싱글톤, 실제 작업 단위는 요청마다 새로 생성 — 이 패턴은 DB를 다루는 프레임워크의 공통 설계인 것 같다. `@Entity`, `@Id`, `@Column`으로 클래스와 테이블을 매핑하고, `find(Menu.class, pk)` 하나로 SELECT를 대체하는 게 아직은 어색하지만 "SQL 없이 객체로 DB를 다룬다"는 JPA의 철학이 처음으로 체감됐다.
