### 학습 내용

#### 1. 엔티티 생명주기 4가지 상태 (`chap01_persistance-context/section03`)

JPA에서 엔티티 객체는 영속성 컨텍스트와의 관계에 따라 4가지 상태를 가진다.

```
비영속(Transient) → persist() → 영속(Managed)
영속(Managed)    → detach/clear/close → 준영속(Detached)
준영속(Detached)  → merge() → 영속(Managed)
영속(Managed)    → remove() → 삭제(Removed)
```

##### 1-1. 비영속 (Transient)

영속성 컨텍스트와 전혀 관계없는 순수 Java 객체 상태.

```java
// DB에서 조회한 영속 객체와 값이 같아도, new로 직접 만든 객체는 비영속
Menu foundMenu = entityManager.find(Menu.class, menuCode);  // 영속
Menu newMenu = new Menu(
    foundMenu.getMenuCode(),
    foundMenu.getMenuName(),
    foundMenu.getMenuPrice(),
    foundMenu.getCategoryCode(),
    foundMenu.getOrderableStatus()
);  // 비영속 — 내용이 같아도 영속성 컨텍스트가 관리하지 않음

assertNotEquals(foundMenu, newMenu);              // 다른 인스턴스
assertTrue(entityManager.contains(foundMenu));    // foundMenu는 관리 중
assertFalse(entityManager.contains(newMenu));     // newMenu는 관리 안 함
```

##### 1-2. 영속 (Managed) — 다른 EntityManager와의 동일성

**서로 다른 EntityManager**로 같은 PK를 조회하면 다른 인스턴스가 반환된다.

```java
// EntityLifeCycle.findMenuByMenuCode()는 호출마다 새 EntityManager 생성
Menu menu1 = lifeCycle.findMenuByMenuCode(menuCode);
Menu menu2 = lifeCycle.findMenuByMenuCode(menuCode);
assertNotEquals(menu1, menu2);  // 다른 EntityManager → 다른 인스턴스
```

**같은 EntityManager**로 같은 PK를 조회하면 1차 캐시 덕분에 동일 인스턴스가 반환된다.

```java
EntityManager entityManager = EntityManagerGenerator.getInstance();
Menu menu1 = entityManager.find(Menu.class, menuCode);
Menu menu2 = entityManager.find(Menu.class, menuCode);
assertEquals(menu1, menu2);  // 같은 EntityManager → 같은 인스턴스 (1차 캐시)
```

##### 1-3. 준영속 (Detached) — detach / merge

`detach()`는 특정 엔티티만 영속성 컨텍스트에서 분리한다. 분리된 객체를 수정해도 DB에 반영되지 않는다.

```java
entityTransaction.begin();
Menu foundMenu = entityManager.find(Menu.class, menuCode);

entityManager.detach(foundMenu);    // 준영속화
foundMenu.setMenuPrice(1000);       // 변경해도 영속성 컨텍스트 미반영
entityManager.flush();

// flush 후에도 DB에는 원래 price가 남아 있음
assertNotEquals(1000, entityManager.find(Menu.class, menuCode).getMenuPrice());
entityTransaction.rollback();
```

`merge()`로 준영속 상태의 객체를 다시 영속 상태로 복귀시킬 수 있다.

```java
entityManager.detach(foundMenu);
foundMenu.setMenuPrice(1000);
entityManager.merge(foundMenu);     // 영속 상태로 복귀
entityManager.flush();

assertEquals(1000, entityManager.find(Menu.class, menuCode).getMenuPrice());
entityTransaction.rollback();
```

##### 1-4. 준영속 — clear / close

- `clear()` : 영속성 컨텍스트 내 **모든** 엔티티를 준영속화 (초기화). EntityManager는 살아 있음.

```java
Menu foundMenu = entityManager.find(Menu.class, menuCode);
entityManager.clear();  // 영속성 컨텍스트 초기화

Menu expectedMenu = entityManager.find(Menu.class, menuCode);  // DB에서 새로 조회
assertNotEquals(foundMenu, expectedMenu);  // clear 전/후 다른 인스턴스
```

- `close()` : 영속성 컨텍스트 자체를 종료. 이후 EntityManager 사용 시 `IllegalStateException` 발생.

```java
entityManager.close();

assertThrows(
    IllegalStateException.class,    // ← IllegalAccessError 아님에 주의
    () -> entityManager.find(Menu.class, menuCode)
);
```

##### 1-5. 삭제 (Removed) — remove

`remove()`는 엔티티를 영속성 컨텍스트와 DB에서 삭제한다. `flush()` 후 `contains()`로 삭제 여부 확인.

```java
entityTransaction.begin();
Menu foundMenu = entityManager.find(Menu.class, menuCode);

entityManager.remove(foundMenu);
entityManager.flush();

assertFalse(entityManager.contains(foundMenu));  // 영속성 컨텍스트에서 제거됨
entityTransaction.rollback();  // 테스트이므로 실제 DB에는 반영하지 않음
```

#### 2. JPA 엔티티 매핑 어노테이션 (`chap02_mapping`)

Spring Boot + Spring Data JPA 환경에서 엔티티 매핑을 다뤘다.

##### 2-1. `application.yml` JPA 설정

```yaml
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/menudb
    username: ohgiraffers
    password: ohgiraffers
  jpa:                          # spring: 하위에 위치해야 함
    show-sql: true
    database: mysql
    hibernate:
      ddl-auto: create          # 앱 실행 시 테이블 자동 생성 (개발용)
    properties:
      hibernate:
        format_sql: true
```

> `jpa:` 블록은 반드시 `spring:` 하위에 들여쓰기 되어야 한다. 최상위에 두면 Spring Boot가 인식하지 못한다.

##### 2-2. 주요 매핑 어노테이션

```java
@Entity(name = "entityMember")       // JPA 엔티티 선언, JPQL에서 사용할 별칭
@Table(name = "tbl_member")          // 매핑 테이블명
public class Member {

    @Id
    @Column(name = "member_no")
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // AUTO_INCREMENT
    private int memberNo;

    @Column(name = "member_id", unique = true, nullable = false, columnDefinition = "varchar(10)")
    private String memberId;

    @Column(name = "member_role")
    @Enumerated(EnumType.ORDINAL)    // enum을 숫자(0, 1, ...)로 저장
    // @Enumerated(EnumType.STRING)  // enum 이름 문자열로 저장 (권장)
    private MemberRole memberRole;

    @Transient                       // DB 컬럼으로 매핑하지 않음
    private String phone;

    protected Member() {}            // JPA 기본 생성자 필수
}
```

| 어노테이션 | 역할 |
|---|---|
| `@Entity` | JPA가 관리하는 엔티티 선언 |
| `@Table(name)` | 클래스명과 테이블명이 다를 때 지정 |
| `@Id` | PK 컬럼 지정 |
| `@GeneratedValue(IDENTITY)` | DB AUTO_INCREMENT에 위임 |
| `@Column` | 컬럼명, 제약조건 등 세부 설정 |
| `@Enumerated` | enum 매핑 방식 지정 (ORDINAL/STRING) |
| `@Transient` | DB 매핑 제외 필드 |

##### 2-3. `EnumType.ORDINAL` vs `EnumType.STRING`

```java
public enum MemberRole {
    ROLE_MEMBER,  // ORDINAL: 0 / STRING: "ROLE_MEMBER"
    ROLE_ADMIN    // ORDINAL: 1 / STRING: "ROLE_ADMIN"
}
```

- `ORDINAL` : 숫자로 저장 → enum 순서가 바뀌면 기존 데이터가 오염됨 (위험)
- `STRING` : 문자열로 저장 → 순서 변경에 안전하지만 저장 공간이 더 필요

##### 2-4. Spring Data JPA — `JpaRepository`

```java
public interface MemberRepository extends JpaRepository<Member, Integer> {
    // 기본 CRUD (save, findById, findAll, delete 등) 자동 제공
}
```

```java
@Service
public class MemberService {
    private MemberRepository memberRepository;

    @Transactional
    public void registMember(MemberRegistDto newMember) {
        Member member = new Member(...);
        memberRepository.save(member);  // INSERT
    }
}
```

### 트러블슈팅

#### persistence.xml에 엔티티 클래스 누락

```xml
<!-- section03의 Menu를 쓰려면 persistence.xml에 명시해야 함 -->
<class>com.ohgiraffers.section02.crud.Menu</class>
<class>com.ohgiraffers.section03.entity.Menu</class>  <!-- 이게 없으면 find()가 동작 안 함 -->
```

#### 테스트 기대 예외 타입 오류

`entityManager.close()` 후 find() 호출 시 발생하는 예외는 `IllegalStateException`이다. `IllegalAccessError`는 JVM 접근 제어 에러로 전혀 다른 개념.

```java
// 틀림
assertThrows(IllegalAccessError.class, () -> entityManager.find(...));

// 맞음
assertThrows(IllegalStateException.class, () -> entityManager.find(...));
```

#### 반복 실행에 깨지는 count 검증

테스트가 실제 DB에 commit하면 실행할 때마다 row 수가 늘어나므로 하드코딩된 count 검증은 두 번째 실행부터 실패한다.

```java
// 틀림 — DB에 29개일 때만 통과
assertEquals(30, afterCount);

// 맞음 — 몇 개든 +1 검증
Long beforeCount = crud.getCountBeforeSave();
Long afterCount = crud.saveAndReturnAllCount(newMenu);
assertEquals(beforeCount + 1, afterCount);
```

### 핵심 정리

엔티티 생명주기 전환 정리

| 상태 | 특징 | 전환 방법 |
|---|---|---|
| 비영속 | 순수 Java 객체, 컨텍스트 무관 | `new` |
| 영속 | 컨텍스트가 관리, 변경 감지 | `persist()`, `find()`, `merge()` |
| 준영속 | 컨텍스트에서 분리, 변경 미반영 | `detach()`, `clear()`, `close()` |
| 삭제 | 컨텍스트 + DB에서 제거 예정 | `remove()` |

- `flush()` : 영속성 컨텍스트의 변경 내용을 DB에 동기화. commit이 아니므로 rollback 가능
- `merge()` : 준영속 객체의 변경 내용을 영속 상태로 병합. 원본 객체가 아닌 **새로운 영속 인스턴스** 반환
- `clear()` 후 같은 PK로 find하면 DB에서 새로 조회하므로 다른 인스턴스가 반환됨

### 느낀 점 / 회고

오늘은 JPA 영속성 컨텍스트의 핵심인 엔티티 생명주기를 테스트 코드로 직접 검증했다.

`detach()`로 특정 엔티티만 분리하고, `flush()`해도 DB에 반영 안 되는 걸 직접 확인하니 "영속성 컨텍스트가 DB와의 중간 버퍼 역할을 한다"는 개념이 손에 잡혔다. `clear()`와 `close()`의 차이도 명확해졌다 — clear는 컨텍스트를 비우되 EntityManager는 살아 있고, close는 아예 문을 닫아버려서 이후 사용이 불가능하다.

트러블슈팅에서 배운 것들이 개념 이해에 더 도움이 됐다. 테스트가 commit을 해버리면 반복 실행 시 count가 계속 늘어난다는 점도, 테스트는 항상 상태에 독립적이어야 한다는 원칙을 다시 상기시켜줬다.

`chap02_mapping`에서는 `@Enumerated(EnumType.ORDINAL)` vs `STRING`의 차이가 인상적이었다. enum 순서가 바뀌면 ORDINAL로 저장된 기존 데이터가 조용히 오염된다는 게 실무에서 진짜 무서운 버그가 될 수 있다. 앞으로 enum 매핑은 무조건 `STRING`을 기본으로 가져가야겠다.
