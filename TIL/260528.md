### 학습 내용

#### 1. Chapter 01 - Request Mapping (`02_spring_boot/chap01_request-mapping`)

##### 1-1. @RequestMapping & HTTP 메서드별 매핑
`@RestController`는 메서드 반환값을 그대로 HTTP 응답 본문으로 보내는 컨트롤러다. 클래스 레벨에 `@RequestMapping`을 붙이면 그 안의 모든 핸들러 메서드에 공통 URL prefix가 붙는다.

```java
@RestController
@RequestMapping("/api/v1/menus") // 이 Controller 안 모든 메서드의 URL prefix
public class MethodMappingTestController {

    @GetMapping     // 조회
    public ResponseEntity<Map<String, String>> findMenus() {
        return ResponseEntity.ok(Map.of("message", "메뉴 목록 조회용 핸들러 메소드 호출"));
    }

    @PostMapping    // 등록
    public ResponseEntity<Map<String, String>> registMenu() {
        return ResponseEntity.status(201).body(Map.of("message", "신규 메뉴 등록용 핸들러 메소드 호출"));
    }

    @PutMapping("/{menuCode}")    // 수정
    public ResponseEntity<Map<String, String>> modifyMenu(@PathVariable int menuCode) {
        return ResponseEntity.ok(Map.of("message", menuCode + "번 메뉴 수정용 핸들러 메소드 호출"));
    }

    @DeleteMapping("/{menuCode}") // 삭제
    public ResponseEntity<Map<String, String>> deleteMenu(@PathVariable int menuCode) {
        return ResponseEntity.ok(Map.of("message", menuCode + "번 메뉴 삭제용 핸들러 메소드 호출"));
    }
}
```

- `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`은 각각 HTTP GET/POST/PUT/DELETE 요청을 처리하는 매핑 어노테이션이다. (`@RequestMapping(method = ...)`의 축약형)
- 같은 URL이라도 **HTTP 메서드가 다르면 다른 핸들러**로 매핑된다 → REST 설계의 기본.

##### 1-2. ResponseEntity로 상태코드 제어
`ResponseEntity`는 응답 본문 + 상태코드 + 헤더를 함께 표현하는 객체다.

- `ResponseEntity.ok(body)` → 200 OK
- `ResponseEntity.status(201).body(body)` → 201 Created
- 등록(POST)은 200이 아니라 **201 Created**를 돌려주는 게 REST 관례.

##### 1-3. 클래스 단위 자원 매핑
리소스(자원) 단위로 컨트롤러를 나누고 클래스에 base URL을 지정한다.

```java
@RestController
@RequestMapping("/api/v1/orders")
public class ClassMappingTestController {

    @GetMapping
    public ResponseEntity<Map<String, Object>> findOrders() { ... }   // GET /api/v1/orders

    @GetMapping("/{orderNumber}")
    public ResponseEntity<Map<String, Object>> selectOrderDetail(@PathVariable int orderNumber) { ... }
    // GET /api/v1/orders/{orderNumber}
}
```

> 목록 조회는 `/orders`, 단건 조회는 `/orders/{id}` 형태. URL은 자원(명사)으로, 행위는 HTTP 메서드로 표현한다.

#### 2. Chapter 02 - Handler Method 파라미터 받기 (`02_spring_boot/chap02_handler-method`)

핸들러 메서드가 요청 데이터를 받는 다양한 방법을 정리. 요청의 어느 위치에서 값을 꺼내느냐에 따라 어노테이션이 달라진다.

##### 2-1. @RequestParam - 쿼리스트링
`?keyword=coffee&categoryCode=2&page=1` 같은 쿼리스트링을 메서드 파라미터로 받는다.

```java
// GET /api/v1/menus?keyword=coffee&categoryCode=2&page=1
@GetMapping
public ResponseEntity<Map<String, Object>> findMenus(
        @RequestParam(required = false) String keyword,
        @RequestParam(defaultValue = "0") int categoryCode,
        @RequestParam(defaultValue = "1") int page
) { ... }
```

- `required = false` → 해당 파라미터가 없어도 에러 안 남(없으면 null).
- `defaultValue = "1"` → 안 들어오면 기본값 사용.
- 파라미터 전체를 한 번에 받고 싶으면 `@RequestParam Map<String, String> parameters`로 Map으로 받을 수 있다.

##### 2-2. @PathVariable - URL 경로 값
URL 경로의 일부를 변수로 받는다.

```java
// GET /api/v1/menus/{menuCode}
@GetMapping("/{menuCode}")
public ResponseEntity<Map<String, Object>> findMenu(@PathVariable int menuCode) { ... }
```

> 쿼리스트링은 "검색/필터 조건", PathVariable은 "특정 자원 식별"에 쓴다는 게 핵심 구분.

##### 2-3. @RequestBody - JSON 본문을 DTO로
POST 요청의 JSON 본문을 객체(DTO)로 변환해서 받는다.

```java
@PostMapping
public ResponseEntity<Map<String, Object>> creatMenu(@RequestBody MenuDto menu) {
    Map<String, Object> response = new LinkedHashMap<>();
    response.put("message", "메뉴 등록 요청 성공");
    response.put("menu", menu);
    return ResponseEntity.status(HttpStatus.CREATED).body(response);
}
```

```json
{ "name": "아이스 아메리카노", "price": 5000, "categoryCode": 2, "orderableStatus": "Y" }
```

- Jackson이 JSON ↔ 객체 변환을 처리한다. 그래서 **DTO에 기본 생성자 + getter/setter**가 필요하다.
- 본문을 가공 없이 그대로 받고 싶으면 `@RequestBody String body`로 문자열로 받을 수도 있다.

##### 2-4. @RequestHeader / @CookieValue - 헤더와 쿠키

```java
@GetMapping("/request-info")
public ResponseEntity<Map<String, Object>> requestInfo(
        @RequestHeader(value = "user-agent", required = false) String userAgent,
        @RequestHeader Map<String, String> headers,           // 헤더 전체
        @CookieValue(value = "JSESSIONID", required = false) String sessionId
) { ... }
```

- `@RequestHeader`로 특정 헤더 / 헤더 전체(Map)를, `@CookieValue`로 쿠키 값을 꺼낸다.

##### 2-5. HttpSession - 세션 다루기
파라미터에 `HttpSession`을 선언하면 현재 요청의 세션 객체를 주입받는다.

```java
@PostMapping("/session")
public ResponseEntity<Map<String, Object>> saveSession(HttpSession session, @RequestParam String id) {
    session.setAttribute("id", id);   // 저장
    ...
}

@GetMapping("/session")
public ResponseEntity<Map<String, Object>> readSession(HttpSession session) {
    session.getAttribute("id");       // 조회
    ...
}

@DeleteMapping("/session")
public ResponseEntity<Map<String, Object>> removeSession(HttpSession session) {
    session.invalidate();             // 세션 만료
    ...
}
```

- `setAttribute` / `getAttribute` / `invalidate`로 세션 값 저장·조회·만료를 처리한다.

##### 2-6. api-test.http로 직접 호출 테스트
IntelliJ HTTP Client(`.http` 파일)로 위 핸들러들을 실제로 호출해보며 응답을 확인했다. GET/POST/PUT/DELETE, 쿼리스트링, JSON 본문, 헤더/쿠키, 세션 시나리오까지 한 파일에서 테스트.

### 핵심 정리

요청 데이터 받는 위치별 어노테이션
- `@RequestParam` → 쿼리스트링 (검색/필터 조건)
- `@PathVariable` → URL 경로 (자원 식별)
- `@RequestBody` → 요청 본문 JSON → DTO (Jackson 변환)
- `@RequestHeader` → 헤더
- `@CookieValue` → 쿠키
- `HttpSession` → 세션 객체 주입

HTTP 메서드별 매핑
- `@GetMapping`(조회) / `@PostMapping`(등록) / `@PutMapping`(수정) / `@DeleteMapping`(삭제)
- 같은 URL + 다른 메서드 = 다른 핸들러

응답
- `ResponseEntity`로 본문 + 상태코드 + 헤더 제어
- 등록 성공은 201 Created

REST URL 설계
- URL은 자원(명사), 행위는 HTTP 메서드로 표현
- 목록 `/menus`, 단건 `/menus/{id}`

### 느낀 점 / 회고

그동안 Codeit·인턴 때 Spring Boot 컨트롤러를 짜면서 `@RequestParam`, `@PathVariable`, `@RequestBody`를 감으로 구분해서 썼는데, 오늘 "요청의 어느 위치(쿼리스트링/경로/본문/헤더/쿠키)에서 값을 꺼내느냐"라는 한 축으로 정리하니까 머릿속이 깔끔해졌다. 특히 쿼리스트링은 검색 조건, PathVariable은 자원 식별이라는 구분 기준이 명확해진 게 수확이다.

`@RequestBody`가 동작하려면 DTO에 기본 생성자랑 getter/setter가 필요하다는 것도 다시 짚었다. Jackson이 빈 객체를 만든 뒤 setter로 값을 채우는 구조라 그렇다는 걸 알고 나니, 예전에 DTO에서 기본 생성자 빠뜨려서 역직렬화 에러 났던 경험이 이제야 설명이 된다.

api-test.http로 직접 호출해본 게 좋았다. Postman 안 켜고 IntelliJ 안에서 바로 GET/POST/세션 시나리오까지 돌려볼 수 있어서 흐름이 안 끊겼다. 실무에서 API 빠르게 검증할 때 유용하게 쓸 것 같다.
