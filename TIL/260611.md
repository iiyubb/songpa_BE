### 학습 내용

#### 1. 임베디드 타입 (`chap02-mapping/section02`)

JPA에서 **값 타입(Value Type)** 을 별도 클래스로 분리해 엔티티에 포함시키는 방식.

##### 1-1. `@Embeddable` / `@Embedded`

```java
@Embeddable                           // 임베디드 타입 선언
public class Price {

    @Column(name = "regular_price")
    private int regularPrice;

    @Column(name = "discount_rate")
    private double discountRate;

    @Column(name = "sell_price")
    private int sellPrice;

    protected Price() {}              // JPA 기본 생성자 필수

    public Price(int regularPrice, double discountRate) {
        validateNagativePrice(regularPrice);
        validateNegativeDiscountRate(discountRate);
        this.regularPrice = regularPrice;
        this.discountRate = discountRate;
        this.sellPrice = calcSellPrice(regularPrice, discountRate);   // 생성 시 자동 계산
    }
}
```

```java
@Entity
@Table(name = "tbl_book")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private int bookNo;

    private String bookTitle;
    private String author;

    @Embedded                         // Price의 컬럼들이 tbl_book에 인라인으로 매핑됨
    private Price price;
}
```

- `@Embeddable` : "나는 다른 엔티티에 포함될 수 있다"고 선언하는 값 클래스
- `@Embedded` : 엔티티 안에 임베디드 타입을 포함시키는 어노테이션
- DB 테이블 구조는 변하지 않고, **Java 객체 모델에서만** 의미 있는 단위로 묶을 수 있다

##### 1-2. 임베디드 타입의 장점 — 캡슐화와 유효성 검증

Price 클래스 안에 검증 로직과 계산 로직을 가둘 수 있다.

```java
private void validateNagativePrice(int regularPrice) {
    if (regularPrice < 0) throw new IllegalArgumentException("가격은 음수일 수 없습니다.");
}

private int calcSellPrice(int regularPrice, double discountRate) {
    return (int) (regularPrice - (regularPrice * discountRate));
}
```

서비스 레이어에서는 단순하게 `new Price(정가, 할인율)` 만 넘기면 된다.

```java
@Transactional
public void registBook(BookRegistDTO newBook) {
    Book book = new Book(
        newBook.getBookTitle(),
        newBook.getAuthor(),
        newBook.getPublisher(),
        newBook.getPublishedDate(),
        new Price(newBook.getRegularPrice(), newBook.getDiscountRate())  // 나머지는 Price가 처리
    );
    bookRepository.save(book);
}
```

#### 2. N:1 연관관계 매핑 (`chap03-association-mapping/section01`)

여러 개의 Menu가 하나의 Category에 속하는 다대일 관계를 JPA로 매핑.

##### 2-1. `@ManyToOne` + `@JoinColumn`

```java
@Entity(name = "menu_and_category")
@Table(name = "tbl_menu")
public class Menu {

    @Id
    private int menuCode;
    private String menuName;
    private int menuPrice;

    @ManyToOne(cascade = CascadeType.PERSIST)   // 영속성 전이
    @JoinColumn(name = "categoryCode")          // FK 컬럼 지정
    private Category category;                  // 객체 참조로 연관관계 표현

    private String orderableStatus;
}
```

- `@ManyToOne` : "나(Menu)는 Category와 N:1 관계다" 선언
- `@JoinColumn(name = "categoryCode")` : FK 컬럼명 지정. 생략하면 JPA가 기본 이름을 추론하지만 명시하는 게 안전
- `category` 필드가 `int categoryCode` 대신 **Category 객체**를 직접 들고 있기 때문에, 조회 시 연관 Category가 함께 로딩됨

##### 2-2. 영속성 전이 `CascadeType.PERSIST`

```java
@ManyToOne(cascade = CascadeType.PERSIST)
private Category category;
```

Menu를 `persist()` 할 때 아직 DB에 없는 새 Category도 함께 insert된다.

```java
// Category가 DB에 없어도 Menu persist 시 함께 저장됨
Menu menu = new Menu(123, "스파게티", 15000, new Category(123, "퓨전분식", null), "Y");
entityManager.persist(menu);  // → Menu INSERT + Category INSERT 자동 실행
```

CASCADE 없이 비영속 Category를 참조하면 `TransientPropertyValueException` 발생.

##### 2-3. JPQL JOIN 쿼리

연관관계가 매핑되어 있으면 JPQL에서 `.` 연산자로 연관 객체를 탐색할 수 있다.

```java
// 순수 SQL이라면 JOIN tbl_category ON ... 을 직접 써야 하지만
// JPQL은 매핑된 연관관계(m.category)를 따라 자동으로 JOIN
String jpql = "SELECT c.categoryName " +
              "FROM menu_and_category m " +
              "JOIN m.category c " +          // 객체 경로로 조인
              "WHERE m.menuCode = :menuCode";

return entityManager.createQuery(jpql, String.class)
        .setParameter("menuCode", menuCode)
        .getSingleResult();
```

- JPQL 엔티티 이름은 `@Entity(name = "menu_and_category")` 의 name 값 사용
- `m.category` 는 FK 컬럼명이 아닌 **필드명**

##### 2-4. DTO ↔ Entity 변환 패턴

```java
// Service에서 DTO를 받아 Entity로 변환 후 Repository에 전달
@Transactional
public void registMenu(MenuDTO menuInfo) {
    Menu menu = new Menu(
        menuInfo.getMenuCode(),
        menuInfo.getMenuName(),
        menuInfo.getMenuPrice(),
        new Category(                                  // 중첩 DTO → 중첩 Entity
            menuInfo.getCategory().getCategoryCode(),
            menuInfo.getCategory().getCategoryName(),
            menuInfo.getCategory().getRefCategoryCode()
        ),
        menuInfo.getOrderableStatus()
    );
    manyToOneRepository.regist(menu);
}
```

### 핵심 정리

| 개념 | 어노테이션 | 특징 |
|---|---|---|
| 임베디드 타입 | `@Embeddable` / `@Embedded` | DB 구조 변경 없이 Java 모델에서만 의미 단위로 묶기 |
| 다대일 연관관계 | `@ManyToOne` + `@JoinColumn` | FK 컬럼 대신 객체 참조로 연관관계 표현 |
| 영속성 전이 | `CascadeType.PERSIST` | 부모 persist 시 연관된 비영속 객체도 함께 insert |
| JPQL 경로 탐색 | `m.category` | 객체 필드명으로 JOIN — FK 컬럼명 아님 |

### 느낀 점 / 회고

`@Embedded` / `@Embeddable` 을 처음 봤을 때는 "그냥 필드를 직접 쓰면 되는데 왜 클래스로 빼지?" 싶었다. 그런데 Price 구현을 보니 이해됐다. 정가와 할인율만 넘기면 판매가를 자동으로 계산하고, 음수 검증도 Price 내부에서 처리한다. 서비스가 이 계산 로직을 들고 있을 필요가 없어진다. 단순한 데이터 묶음이 아니라 **행동을 가진 값 객체**라는 개념이 와닿았다.

연관관계 매핑에서는 `categoryCode` 라는 숫자 대신 `Category` 객체를 직접 참조하는 게 처음엔 낯설었다. 그런데 JPQL에서 `m.category.categoryName` 처럼 `.`으로 바로 탐색할 수 있다는 게 SQL의 JOIN보다 훨씬 직관적이었다. 연관관계를 올바르게 매핑해두면 쿼리 작성이 한결 쉬워진다는 걸 체감했다.

`CascadeType.PERSIST` 는 편리하지만 의도치 않은 insert가 발생할 수 있으니, 정말 "함께 저장되어야 하는 관계"인지 판단하고 써야겠다.
