### 학습 내용

#### 1. Chapter 04 - Exception Handler (`02_spring_boot/chap04_exception-handler`)

##### 1-1. 커스텀 예외 클래스 정의
비즈니스 로직에서 발생하는 예외를 의미 있게 표현하려면 `RuntimeException`을 상속해 커스텀 예외를 만든다.

```java
public class MemberNotFoundException extends RuntimeException {
    public MemberNotFoundException(String message) {
        super(message);
    }
}

public class InvalidMemberRequestException extends RuntimeException {
    public InvalidMemberRequestException(String message) {
        super(message);
    }
}
```

- `RuntimeException`을 상속하면 **unchecked exception**이라 `throws` 선언 없이 던질 수 있다.
- 예외 이름 자체가 "어떤 상황인지"를 코드로 설명한다 → 가독성·유지보수성 향상.

##### 1-2. 공통 에러 응답 구조 — ErrorResponse
API 실패 응답의 JSON 구조를 통일하기 위한 DTO.

```java
public class ErrorResponse {
    private final LocalDateTime timestamp;
    private final int status;
    private final String error;
    private final String message;
    private final String path;

    public ErrorResponse(int status, String error, String message, String path) {
        this.timestamp = LocalDateTime.now(); // 생성 시점 자동 기록
        ...
    }
    // getter만 존재 (Jackson 직렬화용)
}
```

- 프론트엔드는 이 구조를 기준으로 에러 메시지와 상태코드를 파싱한다.
- `final` 필드 + getter만 → 한 번 만들면 바뀌지 않는 불변 객체.

##### 1-3. @RestControllerAdvice + @ExceptionHandler — 전역 예외 처리
`@RestControllerAdvice`를 붙인 클래스 안에 `@ExceptionHandler`로 처리할 예외 타입을 지정하면, 여러 컨트롤러에서 발생한 예외를 **한 곳에서** 받아 JSON 응답으로 내려준다.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MemberNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleMemberNotFound(
            MemberNotFoundException exception,
            HttpServletRequest request) {

        ErrorResponse response = new ErrorResponse(
                HttpStatus.NOT_FOUND.value(),   // 404
                HttpStatus.NOT_FOUND.name(),
                exception.getMessage(),
                request.getRequestURI()
        );
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(response);
    }

    @ExceptionHandler(InvalidMemberRequestException.class)
    public ResponseEntity<ErrorResponse> handleInvalidMemberRequest(...) {
        // 400 Bad Request
        return ResponseEntity.badRequest().body(response);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleException(...) {
        // 500 Internal Server Error — 예상 못한 모든 예외 최후 처리
        return ResponseEntity.internalServerError().body(response);
    }
}
```

- `@ExceptionHandler(Exception.class)`가 마지막 안전망 역할. NPE처럼 예상치 못한 예외도 여기서 잡힌다.
- 예외 종류 → HTTP 상태코드 매핑이 명확해짐: `404 Not Found`, `400 Bad Request`, `500 Internal Server Error`.

##### 1-4. 컨트롤러에서 예외 던지기
비즈니스 검증 실패 시 직접 예외를 throw하고, 실제 처리는 `GlobalExceptionHandler`에 위임한다.

```java
@GetMapping("/{memberNo}")
public ResponseEntity<MemberDto> findMember(@PathVariable int memberNo) {
    MemberDto foundMember = members.stream()
            .filter(member -> member.getNo() == memberNo)
            .findFirst()
            .orElseThrow(() -> new MemberNotFoundException(memberNo + "번 회원을 찾을 수 없습니다."));
    return ResponseEntity.ok(foundMember);
}

@PostMapping
public ResponseEntity<Map<String, Object>> registMember(@RequestBody MemberDto member) {
    if (member.getName() == null || member.getName().isBlank()) {
        throw new InvalidMemberRequestException("회원 이름은 비어 있을 수 없습니다.");
    }
    if (member.getAge() < 0) {
        throw new InvalidMemberRequestException("회원 나이는 0 이상이어야 합니다.");
    }
    ...
}
```

> 컨트롤러는 "예외를 던지는 책임"만, `GlobalExceptionHandler`는 "예외를 받아서 응답으로 바꾸는 책임"만 갖는다 → 관심사 분리.

#### 2. Chapter 05 - File Upload (`02_spring_boot/chap05_file-upload`)

##### 2-1. multipart/form-data — 파일과 일반 값을 함께 보내는 요청 형식
`application/json`은 텍스트 데이터만 담을 수 있다. 파일(바이너리)과 일반 텍스트 값을 **같은 요청**에 함께 보내려면 `multipart/form-data` 형식을 사용한다.

- HTTP 요청 본문을 여러 **part**로 나눠서 보내는 구조.
- 각 part에는 이름(name), 헤더, 실제 데이터가 들어있다.
- 파일 part에는 바이너리 데이터, 텍스트 part에는 일반 문자열이 담긴다.

```
Content-Type: multipart/form-data; boundary=----BoundaryXYZ

------BoundaryXYZ
Content-Disposition: form-data; name="file"; filename="photo.png"
Content-Type: image/png

(바이너리 데이터)
------BoundaryXYZ
Content-Disposition: form-data; name="description"

여름 휴가 사진
------BoundaryXYZ--
```

##### 2-2. MultipartFile — Spring이 업로드 파일을 표현하는 객체
`MultipartFile`은 요청에 포함된 파일 데이터를 Spring이 추상화한 객체다. 파일의 내용물뿐 아니라 메타정보도 함께 제공한다.

```java
file.getOriginalFilename()  // 클라이언트가 보낸 원본 파일명 (예: photo.png)
file.getSize()              // 파일 크기 (bytes)
file.getContentType()       // MIME 타입 (예: image/png, text/plain)
file.isEmpty()              // 비어있는 파일인지 여부
file.transferTo(targetPath) // 파일을 디스크의 실제 경로에 저장
```

##### 2-3. @RequestParam("file") MultipartFile file — Multipart 요청의 file part를 받는 방법
`@RequestBody`는 JSON 본문 전체를 객체로 변환할 때 쓰고, `multipart/form-data`의 각 part는 `@RequestParam`으로 받는다.

```java
@PostMapping("/single")
public ResponseEntity<Map<String, Object>> uploadSingleFile(
        @RequestParam("file") MultipartFile file,              // 파일 part
        @RequestParam(value = "description", required = false) String description  // 텍스트 part
) throws IOException {
    ...
}
```

- `@RequestParam("file")`의 `"file"`은 요청에서 어떤 이름의 part를 꺼낼지 지정하는 **part 이름**이다.
- 다중 파일은 `List<MultipartFile>`로 받는다.

```java
@PostMapping("/multiple")
public ResponseEntity<Map<String, Object>> uploadMultipleFile(
        @RequestParam("files") List<MultipartFile> files,
        ...
) throws IOException { ... }
```

##### 2-4. UUID로 저장 파일명 생성 + 확장자 분리
원본 파일명을 그대로 쓰면 이름 충돌이 발생할 수 있다. UUID로 고유한 저장 파일명을 생성하고, 원본에서 확장자만 분리해 붙인다.

```java
String originFileName = file.getOriginalFilename();

// 마지막 점을 기준으로 확장자 추출 (.png, .txt 등)
int lastDotIndex = originFileName.lastIndexOf(".");
String extension = (lastDotIndex == -1) ? "" : originFileName.substring(lastDotIndex);

// UUID로 고유 파일명 생성
String savedFileName = UUID.randomUUID().toString().replace("-", "") + extension;

Path targetPath = uploadPath.resolve(savedFileName).normalize();
file.transferTo(targetPath); // 실제 디스크에 저장
```

##### 2-5. 다중 파일 업로드 — 부분 실패 시 롤백
여러 파일을 저장하다 중간에 실패하면 이미 저장된 파일들을 삭제해 서버에 쓰레기 파일이 남지 않도록 처리한다.

```java
List<FileDto> uploadFiles = new ArrayList<>();
try {
    for (MultipartFile file : files) {
        uploadFiles.add(saveFile(file, "multiple", description));
    }
} catch (IOException | RuntimeException e) {
    // 이미 저장된 파일 삭제
    for (FileDto uploadedFile : uploadFiles) {
        Files.deleteIfExists(Paths.get(uploadedFile.getFilePath()));
    }
    throw e; // 예외 다시 던짐
}
```

##### 2-6. application.properties — multipart 설정
```properties
spring.servlet.multipart.max-file-size=10MB      # 파일 하나의 최대 크기
spring.servlet.multipart.max-request-size=50MB   # 요청 전체의 최대 크기
file.upload-dir=uploads                           # 저장 루트 경로 (@Value로 주입)
```

- `@Value("${file.upload-dir}")` → properties 값을 컨트롤러 생성자에서 주입받아 업로드 경로로 사용.

#### 3. Chapter 06 - Interceptor (`02_spring_boot/chap06_interceptor`)

##### 3-1. HandlerInterceptor — 컨트롤러 앞뒤에 공통 로직 끼워넣기
인터셉터는 컨트롤러 실행 전(preHandle), 실행 후(postHandle), 뷰 렌더링 완료 후(afterCompletion) 세 시점에 공통 로직을 끼워넣는 구조다. 필터(Filter)와 달리 Spring MVC 레이어 안에서 동작하므로 `HttpServletRequest`, `HttpServletResponse`, Handler 객체에 직접 접근할 수 있다.

```java
public interface HandlerInterceptor {
    boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler);
    void postHandle(...);
    void afterCompletion(..., Exception ex);
}
```

- `preHandle` → `true` 반환 시 요청 계속 진행, `false` 반환 시 컨트롤러 실행 중단.
- 필요한 메서드만 `@Override`해서 구현한다 (default 메서드로 정의돼 있음).

##### 3-2. StopwatchInterceptor — 요청 처리 시간 측정
`preHandle`에서 시작 시간을 `request` 속성에 저장하고, `afterCompletion`에서 꺼내 경과 시간을 계산한다.

```java
@Component
public class StopwatchInterceptor implements HandlerInterceptor {

    private static final String START_TIME = "startTime";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        request.setAttribute(START_TIME, System.currentTimeMillis()); // 요청 객체에 임시 보관
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        // instanceof pattern matching (Java 16+)
        if (request.getAttribute(START_TIME) instanceof Long startTime) {
            long elapsedTime = System.currentTimeMillis() - startTime;
            response.setHeader("X-Elapsed-Time", elapsedTime + "ms"); // 응답 헤더에 기록
        }
    }
}
```

- `request.setAttribute` / `request.getAttribute`로 같은 요청 스코프 안에서 데이터를 주고받는다.
- `instanceof Long startTime` — Java 16 instanceof pattern matching: 타입 검사와 캐스팅을 한 줄에 처리.

##### 3-3. ApiKeyInterceptor — 관리자 API 인증
요청 헤더의 `X-API-KEY` 값을 확인해 유효하지 않으면 컨트롤러 실행 전에 **401 Unauthorized**를 직접 응답하고 `false`를 반환해 요청 흐름을 차단한다.

```java
@Component
public class ApiKeyInterceptor implements HandlerInterceptor {

    private static final String API_KEY_HEADER = "X-API-KEY";
    private static final String VALID_API_KEY = "secret-key";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {

        String apiKey = request.getHeader(API_KEY_HEADER);

        if (VALID_API_KEY.equals(apiKey)) {
            return true; // 인증 성공 → 컨트롤러로 계속
        }

        // 인증 실패 → 직접 응답 작성 후 요청 차단
        response.setStatus(HttpStatus.UNAUTHORIZED.value());
        response.setContentType(MediaType.APPLICATION_JSON_VALUE);
        response.setCharacterEncoding("UTF-8");

        Map<String, Object> errorResponse = new LinkedHashMap<>();
        errorResponse.put("status", 401);
        errorResponse.put("message", "관리자 API를 호출하려면 X-API-KEY 헤더가 필요합니다.");
        response.getWriter().write(objectMapper.writeValueAsString(errorResponse));

        return false; // 컨트롤러 실행 중단
    }
}
```

##### 3-4. 인터셉터 등록 — WebMvcConfigurer
인터셉터는 `@Component`만으로는 동작하지 않는다. `WebMvcConfigurer`의 `addInterceptors`를 통해 **어떤 URL 패턴**에 적용할지 함께 등록해야 한다.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // 모든 요청에 stopwatch 적용
        registry.addInterceptor(stopwatchInterceptor)
                .addPathPatterns("/**");

        // /admin/** 요청에만 API Key 인증 적용
        registry.addInterceptor(apiKeyInterceptor)
                .addPathPatterns("/api/v1/admin/**");
    }
}
```

- `addPathPatterns` → 인터셉터를 적용할 URL 패턴 지정.
- `excludePathPatterns` → 특정 경로 제외(로그인 페이지, 정적 리소스 등).

### 핵심 정리

예외 처리 흐름
- `RuntimeException` 상속 → 커스텀 예외 클래스 정의 (의미 있는 이름)
- 컨트롤러에서 throw → `@RestControllerAdvice` + `@ExceptionHandler`가 받아서 JSON 응답 생성
- 예외 종류별 HTTP 상태코드: `404` Not Found / `400` Bad Request / `500` Internal Server Error
- `ErrorResponse` DTO로 공통 에러 응답 구조 통일

파일 업로드 흐름
- 요청 형식: `multipart/form-data` = 파일(바이너리) + 텍스트를 함께 전송하는 HTTP 요청 형식
- `MultipartFile` = Spring이 업로드 파일을 표현하는 객체 (원본명, 크기, MIME, 저장 메서드 제공)
- `@RequestParam("file") MultipartFile file` = Multipart 요청의 file part를 받는 방법
- UUID로 저장 파일명 생성 → 이름 충돌 방지
- 다중 파일 중간 실패 시 이미 저장된 파일 삭제 → 일관성 유지

인터셉터 구조
- `HandlerInterceptor` 구현 → `preHandle`(전) / `afterCompletion`(후) 재정의
- `preHandle` 반환값: `true` = 계속, `false` = 차단
- `@Component` + `WebMvcConfigurer.addInterceptors`로 등록 및 URL 패턴 지정
- 용도: 공통 인증(API Key), 성능 측정, 로깅 등

### 느낀 점 / 회고

오늘 세 챕터를 한꺼번에 쭉 흐름으로 보고 나니, 각각이 "요청-응답 파이프라인의 어느 지점을 다루는가"라는 관점으로 연결된다는 걸 느꼈다. 인터셉터는 컨트롤러 진입 직전·직후, 예외 핸들러는 컨트롤러 실행 중 발생한 예외, 파일 업로드는 컨트롤러가 특수한 요청 본문을 받는 방법—이렇게 보니 퍼즐 조각이 맞춰지는 느낌이었다.

`@RestControllerAdvice` + `@ExceptionHandler` 조합은 오늘 직접 구조를 보면서 `@ControllerAdvice`(여러 컨트롤러 전역 적용)와 `@ResponseBody`(JSON 반환)를 합친 것임을 제대로 이해했다. 예외 핸들러 메서드에 `HttpServletRequest request`를 파라미터로 받으면 요청 URI까지 `ErrorResponse`에 담을 수 있다는 것도 실용적인 포인트였다.

파일 업로드에서 `multipart/form-data`가 왜 필요한지도 이번에 명확해졌다. JSON은 텍스트 기반이라 바이너리 파일을 직접 담을 수 없기 때문에 본문을 여러 part로 나눠 보내는 방식이 필요하다는 것, 그리고 Spring이 그 part 하나하나를 `@RequestParam`으로 꺼낼 수 있게 추상화해놨다는 게 핵심이었다.

인터셉터에서 `request.setAttribute`로 시작 시간을 `preHandle`에 저장하고 `afterCompletion`에서 꺼내는 패턴이 인상적이었다. 같은 요청 스코프를 공유한다는 걸 활용한 깔끔한 방법이었다. API Key 인터셉터에서 `preHandle`이 `false`를 반환하면 컨트롤러 자체가 실행되지 않는다는 것, 그리고 이때 `GlobalExceptionHandler`도 동작하지 않으므로 응답을 인터셉터 안에서 직접 `response`에 써야 한다는 점도 기억해둬야 할 부분이다.
