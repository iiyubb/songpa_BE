### 학습 내용

#### 1. Chapter 04 - Bean 스코프 (`chap04_bean/section01`)

##### 1-1. Singleton - 기본 스코프 (`scope/singleton`)
Spring Bean의 **기본 스코프는 singleton**이다. 컨테이너 안에서 빈을 딱 하나만 만들어두고 여러 곳에서 공유한다. `getBean()`을 몇 번 호출하든 항상 같은 객체를 돌려준다.

```java
@Bean
public ShoppingCart cart() {
    return new ShoppingCart();   // @Scope 생략 → singleton
}
```

```java
ShoppingCart cart1 = context.getBean("cart", ShoppingCart.class);
cart1.addItem(carpBread);
cart1.addItem(milk);

ShoppingCart cart2 = context.getBean("cart", ShoppingCart.class);
cart2.addItem(water);

System.out.println(cart1.hashCode());   // 같은 값
System.out.println(cart2.hashCode());   // 같은 값
```

- `cart1`, `cart2`를 따로 받아도 **같은 인스턴스**라 `hashCode()`가 동일하게 찍힌다.
- 그래서 `cart2`에만 담은 `water`가 `cart1`에서도 그대로 보인다.
- 핵심 주의점: **상태(state)를 가지는 객체를 singleton으로 두면 의도하지 않은 공유 문제**가 생긴다. 장바구니처럼 사용자/요청마다 달라야 하는 객체를 싱글톤으로 두면 안 된다.

##### 1-2. Prototype (`scope/prototype`)
`@Scope("prototype")`을 붙이면 **`getBean()`으로 요청할 때마다 새 객체**를 만들어 반환한다.

```java
@Bean
@Scope("prototype")   // 요청할 때마다 새 객체 생성
public ShoppingCart cart() {
    return new ShoppingCart();
}
```

- `cart1`, `cart2`가 서로 다른 인스턴스 → `hashCode()`가 다르게 찍히고 상태도 공유되지 않는다.

| 구분 | Singleton | Prototype |
| --- | --- | --- |
| 생성 시점 | 컨테이너 초기화 시 1회 | `getBean()` 호출 시마다 |
| 인스턴스 수 | 1개 (공유) | 요청 횟수만큼 |
| 상태 공유 | 됨 (주의 필요) | 안 됨 |

> 상태가 없는 서비스/DAO/리포지토리는 싱글톤이 적합하고, 요청마다 달라야 하는 상태 객체는 prototype을 고려한다.

#### 2. Chapter 04 - Bean 생명주기 init / destroy (`chap04_bean/section02`)

Bean도 **생성·초기화 → 사용 → 소멸**의 생명주기를 가진다. 그 시점에 끼워 넣을 콜백을 지정할 수 있다.

```java
public class Owner {

    @PostConstruct   // 생성 + 의존성 주입 완료 직후 호출
    public void openShop() {
        System.out.println("가게 문을 열었습니다.");
    }

    @PreDestroy      // 컨테이너 종료(Bean 소멸) 직전 호출
    public void closeShop() {
        System.out.println("가게 문을 닫았습니다.");
    }
}
```

```java
// Bean 생성 및 초기화 → @PostConstruct 실행
ApplicationContext context = new AnnotationConfigApplicationContext(ContextConfiguration.class);

// 컨테이너 종료 → @PreDestroy 실행
((AnnotationConfigApplicationContext) context).close();
```

- `@PostConstruct` / `@PreDestroy`는 `jakarta.annotation` 패키지 소속(자바 표준 어노테이션).
- 같은 일을 `@Bean(initMethod = "openShop", destroyMethod = "closeShop")` 속성으로도 지정할 수 있다. (어노테이션 방식과 양자택일)
- `close()`를 호출해야 컨테이너가 종료되며 소멸 콜백이 실행된다.
- **주의**: 소멸 콜백(`@PreDestroy`)은 **singleton 스코프에서만 보장**된다. prototype은 생성 후 컨테이너가 끝까지 관리하지 않아서 소멸 시점을 보장하지 않는다.

#### 3. Chapter 04 - 외부 설정값 주입 @PropertySource & @Value (`chap04_bean/section03`)

값을 코드에 하드코딩하지 않고 **`.properties` 파일에서 읽어와 주입**하는 방식.

```properties
# resources/section03/properties/product-info.properties
bread.carpbread.name=붕어빵
bread.carpbread.price=1000
beverage.milk.name=딸기우유
beverage.milk.capacity=180
beverage.milk.price=1500
```

```java
@PropertySource("section03/properties/product-info.properties")   // 파일 위치 지정
@Configuration
public class ContextConfiguration {

    @Value("${bread.carpbread.name}")
    private String carpBreadName;
    @Value("${bread.carpbread.price}")
    private int carpBreadPrice;

    @Bean
    public Product carpBread() {
        return new Bread(carpBreadName, carpBreadPrice, new Date());
    }
}
```

- `@PropertySource`로 파일을 등록하고, `@Value("${key}")`로 개별 값을 꺼낸다.
- `@Value`는 **필드 주입**뿐 아니라 **메서드 파라미터**에도 쓸 수 있다.

```java
@Bean
public Product water(@Value("${beverage.water.name}") String waterName,
                     @Value("${beverage.water.price}") int waterPrice,
                     @Value("${beverage.water.capacity}") int waterCapacity) {
    return new Beverage(waterName, waterPrice, waterCapacity);
}
```

> `${...}` 자리표시자는 PropertySourcesPlaceholderConfigurer가 실제 값으로 치환한다. Spring Boot의 `application.yml` + `@Value` / `@ConfigurationProperties`로 이어지는 설정 외부화의 출발점.

#### 4. Chapter 05 - AOP (`chap05_aop/section01`)

##### 4-1. AOP란
**관점 지향 프로그래밍(Aspect Oriented Programming)**. 로깅·트랜잭션·보안처럼 여러 메서드에 공통으로 끼어드는 **부가 기능(횡단 관심사)** 을, 핵심 비즈니스 로직과 분리해서 한 곳에 모아 관리하는 방식이다. Spring은 실제 대상 객체 앞에 **프록시(대리 객체)** 를 세우고, 그 프록시가 메서드 실행 전후로 공통 기능을 끼워 넣는다.

```java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)   // AOP 프록시 활성화
public class ContextConfiguration {
}
```

- `proxyTargetClass = true` → 인터페이스가 없어도 CGLIB로 클래스 기반 프록시를 만든다.

##### 4-2. 핵심 용어

| 용어 | 의미 |
| --- | --- |
| **Aspect** | 부가 기능 + 적용 규칙을 모은 클래스 (`@Aspect`) |
| **Advice** | 언제 무엇을 할지 (`@Before`, `@After`, `@Around` 등) |
| **Pointcut** | 어떤 메서드에 적용할지 고르는 조건식 |
| **JoinPoint** | Advice가 적용되는 실행 지점 (현재 실행 정보를 담은 객체) |

##### 4-3. Aspect 작성 예제

```java
@Aspect        // AOP용 클래스 표시
@Component
public class LoggingAspect {

    // Pointcut: section01 패키지 안의 *Service 클래스의 모든 메서드 실행 지점
    @Pointcut("execution(* com.ohgiraffers.section01.*Service.*(..))")
    public void logPointcut() {}

    @Before("LoggingAspect.logPointcut()")   // 대상 메서드 실행 "전"에 끼어듦
    public void logBefore(JoinPoint joinPoint) {
        System.out.println("Before getTarget(): " + joinPoint.getTarget());      // 실제 대상 객체
        System.out.println("Before getSignature(): " + joinPoint.getSignature()); // 실행 메서드 시그니처
    }
}
```

- **Pointcut 표현식** `execution(* com.ohgiraffers.section01.*Service.*(..))` 해석
  - `*` (첫 번째) : 반환 타입 무관
  - `com.ohgiraffers.section01.*Service` : 해당 패키지의 이름이 `Service`로 끝나는 클래스
  - `.*(..)` : 모든 메서드, 모든 파라미터
- `@Before`로 등록하면 `memberService.selectMembers()`, `selectMember(1L)` 호출 시 **메서드 본문 실행 전에** `logBefore`가 먼저 실행된다.
- `JoinPoint`로 대상 객체(`getTarget`)와 실행 메서드 정보(`getSignature`)에 접근할 수 있다.

##### 4-4. 동작 구조

```
context.getBean("memberService")
    → 실제 MemberService가 아니라 "프록시 객체"가 반환됨
        ↓ selectMembers() 호출
    [프록시] → @Before logBefore() 실행
            → 실제 MemberService.selectMembers() 실행
            → MemberDao.selectMembers() 실행
```

- `@Service`, `@Repository`, `@Component`로 빈을 등록하고, 생성자가 하나면 `@Autowired` 생략 가능(생성자 주입).
- 정리하자면 Spring의 `@Transactional`도 결국 이 AOP 프록시 메커니즘 위에서 동작한다.

build.gradle 의존성:
```gradle
implementation 'org.springframework:spring-aop:7.0.7'
implementation 'org.aspectj:aspectjweaver:1.9.19'
implementation 'org.aspectj:aspectjrt:1.9.19'
```

### 핵심 정리

@Component = Spring이 관리할 일반 Bean
@Controller = 웹 요청 처리 계층 bean
@Service = 비즈니스 로직 계층 bean
@Repository = 데이터 접근 계층 bean
@Autowired = 필요한 의존 객체를 자동으로 주입

주입방식
1. 필드주입
2. setter 주입
3. 생성자 주입

@Primary = 기본 우선 Bean 지정
@Qualifier = 이름으로 특정 Bean 지정
List<T> 주입 = 같은 타입 Bean 여러 개를 한번에 주입

<Bean 생명주기>
1. Bean 생성
2. 의존성 주입
3. 초기화
4. 사용
5. 소멸
- initMethod, destroyMethod로 특정 시점에 메소드를 실행할 수 있다
- @PostConstruct, @PreDestroy 방식도 있음(참고)

<Bean scope>
- singleton: Container 안에서 하나만 만들어지고 공유
- property: getBean() 호출 때마다 새로 만들어짐

<외부 설정값>
- 변경 가능성이 있는 값은 java 코드에 직접 박아두지 않는 것이 좋다
- properties 파일에 값을 작성하고 @PropertySource, @Value로 읽을 수 있다

### 느낀 점 / 회고

chap04에서 가장 와닿은 건 싱글톤의 상태 공유 문제였다. 그동안 `@Service`, `@Repository`에 별생각 없이 어노테이션을 붙여왔는데, 이게 전부 싱글톤이고 "그래서 상태(필드)를 함부로 두면 안 된다"는 게 코드로 hashCode를 찍어보니 명확하게 보였다. 실무에서 서비스 빈에 가변 필드를 두면 동시성 버그로 이어진다는 얘기가 왜 나오는지 이제 이해된다.

chap05 AOP는 면접에서 자주 나오는 주제라 직접 짜본 게 의미가 컸다. `@Transactional`이 "프록시가 메서드 앞뒤를 감싸서 트랜잭션을 열고 닫는다"는 설명을 그동안 외우기만 했는데, `@Before` advice가 실제 메서드 전에 끼어드는 흐름을 눈으로 확인하니 프록시 기반 AOP의 그림이 잡혔다. 같은 클래스 내부 메서드 호출은 프록시를 안 거쳐서 AOP가 안 먹는다는 self-invocation 이슈도 이 구조를 이해하니 자연스럽게 납득됐다. RAG/AI Agent 쪽 작업을 하더라도 공통 로깅이나 호출 추적을 AOP로 분리하는 패턴은 그대로 쓸 수 있을 것 같다.
