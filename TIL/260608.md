### 학습 내용

#### 1. Chapter 04 - Dynamic Query 추가 실습 (`10_mybatis/chap04_dynamic-query`)

##### 1-1. `<if>`로 가격 범위 다단계 필터링

단일 조건이 아닌 여러 범위를 독립적인 `<if>`로 구성해 파라미터 값에 따라 적절한 범위 조건을 추가한다.

```xml
<select id="selectMenuByPrice" parameterType="hashmap" resultMap="menuResultMap">
    SELECT ... FROM TBL_MENU A
    WHERE A.ORDERABLE_STATUS = 'Y'

    <if test="price gte 0 and price lte 10000">
        <![CDATA[ AND A.MENU_PRICE < #{ price } ]]>
    </if>
    <if test="price gt 10000 and price lte 20000">
        AND A.MENU_PRICE BETWEEN 10000 AND #{ price }
    </if>
    <if test="price gt 20000 and price lte 30000">
        AND A.MENU_PRICE BETWEEN 20000 AND #{ price }
    </if>
    <if test="price gt 30000">
        AND A.MENU_PRICE BETWEEN 30000 AND #{ price }
    </if>
    ORDER BY A.MENU_CODE
</select>
```

- 조건들은 상호 배타적이므로 한 번에 하나만 추가됨
- `<![CDATA[ ]]>` : XML 파서가 `<` 기호를 태그로 인식하지 않도록 감쌈

##### 1-2. `<if>`로 동적 JOIN + 조건 분기

`condition` 값에 따라 JOIN 여부와 WHERE 절 조건을 다르게 적용:

```xml
<select id="searchMenu" parameterType="SearchCriteria" resultMap="menuResultMap">
    SELECT ... FROM TBL_MENU A

    <if test="condition == 'category'">
        JOIN tbl_category B ON (A.CATEGORY_CODE = B.CATEGORY_CODE)
    </if>
    WHERE A.ORDERABLE_STATUS = 'Y'

    <if test="condition == 'name'">
        AND A.MENU_NAME LIKE CONCAT('%', #{ value }, '%')
    </if>
    <if test="condition == 'category'">
        AND B.CATEGORY_NAME = #{value}
    </if>
</select>
```

검색 조건을 담는 DTO를 별도로 만들어 파라미터로 전달:

```java
public class SearchCriteria {
    private String condition; // "name" or "category"
    private String value;
}
```

이어서 학습할 태그: `<choose>/<when>/<otherwise>`, `<foreach>`, `<where>`, `<trim>`, `<set>`

#### 2. Chapter 05 - Spring Boot + MyBatis 통합 (`10_mybatis/chap05_spring-mybatis`)

순수 MyBatis는 `SqlSessionFactory` 관리, `SqlSession` 열고 닫기, `commit()`/`rollback()` 직접 호출이 필요했다. Spring Boot와 통합하면 이 모든 보일러플레이트가 자동화된다.

##### 2-1. 설정 — `application.yml` + `@MapperScan`

```yaml
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/menudb
    username: ohgiraffers
    password: ohgiraffers

mybatis:
  mapper-locations: mappers/**/*.xml  # XML Mapper 파일 위치 패턴
```

```java
@SpringBootApplication
@ComponentScan(basePackages = "com.ohgiraffers.springmybatis")
@MapperScan(basePackages = "com.ohgiraffers.springmybatis", annotationClass = Mapper.class)
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

- `mybatis.mapper-locations` : XML Mapper 파일 위치를 패턴으로 지정 (클래스패스 기준)
- `@MapperScan` : 지정한 패키지에서 `@Mapper`가 붙은 인터페이스를 스캔해 Spring Bean으로 등록

##### 2-2. Mapper 인터페이스 — `@Mapper`

```java
@Mapper
public interface MenuMapper {
    List<MenuDto> findAllMenu();
    MenuDto findMenuByCode(@Param("menuCode") int menuCode);
    List<CategoryDto> findAllCategory();
    int registMenu(MenuDto menu);
    int modifyMenu(MenuDto menu);
    int deleteMenu(@Param("menuCode") int menuCode);
}
```

- `@Mapper` : Spring이 이 인터페이스의 프록시 구현체를 자동 생성해 Bean으로 등록
- `@Param("menuCode")` : 단일 기본형 파라미터에 이름을 붙여 XML에서 `#{ menuCode }`로 참조
- XML과의 연결 규칙은 순수 MyBatis와 동일 (namespace = 풀 클래스명, id = 메서드명)

##### 2-3. Service — `@Transactional`로 트랜잭션 자동 관리

```java
@Service
public class MenuService {

    private final MenuMapper menuMapper;

    public MenuService(MenuMapper menuMapper) {
        this.menuMapper = menuMapper;
    }

    public List<MenuDto> findAllMenu() {
        return menuMapper.findAllMenu(); // 조회는 @Transactional 불필요
    }

    @Transactional
    public MenuDto registNewMenu(MenuDto menu) {
        menuMapper.registMenu(menu);
        return menu; // INSERT 후 useGeneratedKeys로 채워진 code 포함
    }

    @Transactional
    public boolean modifyMenu(MenuDto menu) {
        return menuMapper.modifyMenu(menu) > 0;
    }

    @Transactional
    public boolean deleteMenu(int menuCode) {
        return menuMapper.deleteMenu(menuCode) > 0;
    }
}
```

순수 MyBatis의 `try-catch-finally` + `commit()`/`rollback()`/`close()` 패턴이 `@Transactional` 어노테이션 하나로 대체된다. 예외 발생 시 자동 롤백, 정상 종료 시 자동 커밋.

##### 2-4. Mapper XML — `useGeneratedKeys`와 소프트 삭제

```xml
<!-- INSERT: DB 자동 생성 key를 DTO에 다시 채워줌 -->
<insert id="registMenu" parameterType="com.ohgiraffers.springmybatis.menu.model.dto.MenuDto"
        useGeneratedKeys="true" keyProperty="code">
    insert into tbl_menu (menu_name, menu_price, category_code, orderable_status)
    values ( #{ name }, #{ price }, #{ categoryCode }, #{ orderableStatus } )
</insert>

<!-- DELETE: 물리 삭제 대신 orderable_status를 'N'으로 변경 -->
<update id="deleteMenu" parameterType="_int">
    update tbl_menu
        set orderable_status = 'N'
    where menu_code = #{ menuCode }
</update>
```

- `useGeneratedKeys="true"` : DB가 생성한 AUTO_INCREMENT 값을 받아옴
- `keyProperty="code"` : 받아온 값을 DTO의 `code` 필드에 주입 → INSERT 후 `menu.getCode()`로 조회 가능
- 소프트 삭제 : `DELETE` 대신 `UPDATE`로 상태 컬럼만 바꿔 데이터를 논리적으로 삭제

##### 2-5. Controller — REST API

```java
@RestController
@RequestMapping("/api/v1")
@CrossOrigin(origins = "*")
public class MenuController {

    @GetMapping("/menus")
    public ResponseEntity<List<MenuDto>> findMenuList() {
        return ResponseEntity.ok(menuService.findAllMenu());
    }

    @GetMapping("/menus/{menuCode}")
    public ResponseEntity<MenuDto> findMenuByCode(@PathVariable int menuCode) {
        MenuDto menu = menuService.findMenuByCode(menuCode);
        if (menu == null) return ResponseEntity.notFound().build();
        return ResponseEntity.ok(menu);
    }

    @PostMapping("/menus")
    public ResponseEntity<MenuDto> registMenu(@RequestBody MenuDto menu) {
        MenuDto newMenu = menuService.registNewMenu(menu);
        return ResponseEntity.status(HttpStatus.CREATED).body(newMenu);
    }

    @PutMapping("/menus/{menuCode}")
    public ResponseEntity<Void> modifyMenu(@PathVariable int menuCode, @RequestBody MenuDto menu) {
        menu.setCode(menuCode);
        if (!menuService.modifyMenu(menu)) return ResponseEntity.notFound().build();
        return ResponseEntity.noContent().build();
    }

    @DeleteMapping("/menus/{menuCode}")
    public ResponseEntity<Void> deleteMenu(@PathVariable int menuCode) {
        if (!menuService.deleteMenu(menuCode)) return ResponseEntity.notFound().build();
        return ResponseEntity.noContent().build();
    }
}
```

| HTTP 메서드 | 엔드포인트 | 응답 상태 |
|---|---|---|
| GET | `/api/v1/menus` | 200 OK |
| GET | `/api/v1/menus/{code}` | 200 OK / 404 Not Found |
| GET | `/api/v1/categories` | 200 OK |
| POST | `/api/v1/menus` | 201 Created |
| PUT | `/api/v1/menus/{code}` | 204 No Content / 404 Not Found |
| DELETE | `/api/v1/menus/{code}` | 204 No Content / 404 Not Found |

- `@CrossOrigin(origins = "*")` : 브라우저의 CORS 정책 우회, 다른 Origin에서 API 호출 허용
- `ResponseEntity.noContent().build()` : body 없이 204 상태 코드만 반환

### 핵심 정리

순수 MyBatis vs Spring Boot MyBatis 비교

| 항목 | 순수 MyBatis | Spring Boot MyBatis |
|---|---|---|
| DataSource 설정 | `mybatis-config.xml` 또는 Java Config | `application.yml` |
| Mapper 등록 | `configuration.addMapper()` | `@MapperScan` + `@Mapper` |
| SqlSession 관리 | 직접 열고 닫음 (`try-finally`) | Spring이 자동 관리 |
| 트랜잭션 | `commit()`/`rollback()` 직접 호출 | `@Transactional` |
| Mapper 사용 | `sqlSession.getMapper(Mapper.class)` | 생성자 주입으로 바로 사용 |

`useGeneratedKeys` + `keyProperty`
- INSERT 후 DB가 생성한 PK 값이 필요할 때 사용
- `useGeneratedKeys="true"` → JDBC의 `getGeneratedKeys()` 호출
- `keyProperty="code"` → 반환된 키를 DTO 필드에 자동 주입

소프트 삭제 패턴
- 실제 DELETE 대신 상태 컬럼(`orderable_status`)을 'N'으로 UPDATE
- 데이터 복구 가능, 참조 무결성 유지, 감사 로그 보존

`@Param` 사용 규칙
- DTO 객체 파라미터 → XML에서 `#{ fieldName }` 직접 접근, `@Param` 불필요
- 단일 기본형(`int`, `String`) → `@Param("이름")`으로 XML 파라미터 이름 명시

### 느낀 점 / 회고

오늘 순수 MyBatis에서 Spring Boot + MyBatis로 넘어오면서 가장 크게 느낀 건 "프레임워크가 대신 해주는 일의 범위"가 얼마나 늘어났는가였다. 어제까지 `SqlSession` 열기 → 트랜잭션 처리 → `finally`에서 `close()` 호출하는 패턴을 매번 직접 썼는데, Spring Boot 환경에서는 `@Transactional` 하나와 생성자 주입으로 끝난다. 보일러플레이트가 사라지니 서비스 클래스가 실제 비즈니스 로직만 담게 돼 가독성이 훨씬 좋아졌다.

`useGeneratedKeys="true"` + `keyProperty`는 처음 보는 기능이었는데, INSERT 후 생성된 PK를 다시 DTO에 주입해준다는 게 실용적이었다. INSERT 직후 응답에서 생성된 id를 클라이언트에 돌려줘야 할 때(예: POST → 201 Created + 생성된 리소스 반환) 별도 SELECT 없이 바로 쓸 수 있다.

소프트 삭제 패턴도 오늘 코드에서 확실히 이해됐다. `deleteMenu`가 실제로는 `UPDATE orderable_status = 'N'`이라는 것 — 데이터를 지우지 않고 논리적으로만 비활성화하는 방식이다. 처음엔 "왜 DELETE를 안 쓰지?" 싶었는데, 이렇게 하면 나중에 복구도 가능하고, 다른 테이블에서 참조 중인 데이터를 지웠을 때 발생하는 외래키 오류도 피할 수 있다는 게 납득됐다.

REST API 응답 코드 처리(200/201/204/404)를 `ResponseEntity`로 명시적으로 구분하는 패턴도 처음 제대로 적용해봤다. 단순히 데이터만 반환하는 게 아니라 "이 요청이 어떤 성격의 응답인지"를 HTTP 상태 코드로 표현한다는 HTTP 설계 원칙이 코드에 녹아있다는 걸 느꼈다.
